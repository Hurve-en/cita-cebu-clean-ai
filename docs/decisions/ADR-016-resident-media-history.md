# ADR-016: Private resident photos and saved scan history

Date: 2026-10-27
Status: Implemented and validated locally; hosted Storage/device acceptance pending
Branch: feat/resident-media-history
Baseline: main 924211aa (resident report submission PR #15)

## Problem and scope

Real reports currently contain text only. Real scanner results are transient even
though the demo has a separate local history store. A successful local analysis is
not evidence that its photo/result was persisted to a real account. Storage upload,
application metadata and deletion can fail independently and require explicit states.

This slice adds one optional photo per saved report, automatic account saving of
completed on-device scan photos/results, history/detail viewing and removal. Photos
are added FROM REPORT DETAILS after the existing atomic text submission succeeds.
The text command and its retry receipt are not changed. A failed photo upload never
undoes a submitted report or claims the photo is attached. The UI explains this
separate optional step before and after report submission.

Rewards, officer/admin mutations, notifications, account deletion, Android/web local
classification, model replacement and server-side inference remain outside scope.
Only eligible residents can perform media commands. Staff media access is deliberately
not opened by this slice; it needs its own assignment/MFA authorization work.

## Data and state machine

Drizzle owns public.resident_media and its schema snapshot. A reviewed custom migration
owns RPCs, app-table grants/RLS and Storage policies. Supabase CLI is the only deploy
ledger. The original six migrations and their historical mappings are preserved.
Provider-owned storage.objects/storage.buckets are not modeled/generated by Drizzle.

Metadata includes owner/request UUIDs, kind, optional owned report ID, exact byte size,
server creation/readiness times and scan label/score/model identity when applicable.
Scan labels match the bundled six-class MobileNetV2 model. Scores are canonical decimal
strings of up to eight places to keep request replay deterministic; they are not
calibrated certainty, proof of sorting, reward eligibility or trusted server inference.
The model identifier is tied to the bundled ONNX SHA prefix d0744dc70738.

States: uploading -> ready; uploading/ready -> delete_pending -> deleted. Deleted rows
retain owner, request key, kind, size and timestamps as retry tombstones, while report
link, scan label, score, model identity and ready timestamp are cleared. Deleted rows
are hidden by RLS and cannot be resurrected by an old request key. Future account
retention/erasure must explicitly handle these minimal retained identifiers.

prepare_resident_media derives the actor from auth.uid(), locks account_access FOR
UPDATE, checks resident role/enabled/ready/verified eligibility, validates shape and
size, checks bucket configuration, and returns or creates an owner-scoped reservation.
A key reused with different metadata is rejected. A report link must belong to the
actor. Report photos do not require the report's original community to remain the
current selection. Unique active report linkage permits one photo at a time; remove
it before adding another. Limit: 200 nondeleted scans and five uploading reservations
per resident. No automatic eviction of existing records occurs.

finalize_resident_media requires the exact reserved object path, owner_id, MIME and
size in Storage metadata before marking a row ready. Missing objects return P0002;
other mismatches fail without changing state. A replay of a ready record returns it.
Storage byte uploads are not in the PostgreSQL transaction: this staged design makes
incompleteness explicit rather than claiming distributed atomicity.

## Storage authorization

One operator-created PRIVATE bucket: resident-media, maximum 2097152 bytes, allowed
MIME types exactly image/jpeg. Configuration uses Dashboard/Storage API. The migration
does not insert/delete provider metadata. Preparation refuses missing/misconfigured
bucket settings. An operator making a private bucket public can expose its existing
objects; operators remain a trust boundary and must never switch this bucket public.

Paths are owner UUID / SERVER-GENERATED MEDIA UUID.jpg, never user-selected filenames.
The client uploads an ArrayBuffer with upsert=false and image/jpeg. Storage INSERT
requires an eligible resident's matching uploading reservation and object owner_id.
SELECT permits only the owner's nondeleted reservation; DELETE requires delete_pending.
UPDATE/move/overwrite is blocked for this bucket. Three narrow permissive policies
are paired with four bucket-specific restrictive guards, so an unrelated broad
permissive policy cannot open resident-media. Other buckets keep their own policies.

The Storage policy helper takes a shared lock on the matching media row during
metadata insertion/removal. Finalization and delete-state commands take update locks.
The account row serializes resident commands and reserve/cancel races. Actual
multi-connection/provider timing still requires hosted verification.

Photos use 60-second signed URLs obtained with the owner's pinned JWT. URLs stay in
component memory, are never persisted/logged, and Image cachePolicy=none avoids an
intentional app disk image cache. A signed URL is a bearer capability until expiry;
logout/deletion/revocation does not retroactively invalidate a link already issued.
Downloaded or shared copies cannot be recalled. Operator access/backups and OS/browser
caches also remain outside a claim of immediate physical erasure.

## Safe retries and session isolation

Native uploads save a resized JPEG and JSON retry manifest under a separate owner UUID
directory in app Documents before any remote prepare/upload. Web stores bytes plus
metadata atomically in IndexedDB. The app reads back the pending manifest and byte
length before sending. It preserves corrupt data instead of overwriting it. These
copies are NOT additionally encrypted by this feature, persist across logout, and are
removed after confirmed saving/cancellation/removal. App uninstall/browser storage
clearing can destroy an unfinished retry copy. A crash before manifest persistence
can leave an unindexed native JPEG; full storage reconciliation is future work.

A retry first prepares/replays the same key and attempts finalization before uploading
again. Thus an upload or final response lost AFTER success confirms the existing file
without another overwrite. An upload conflict is never treated as success by itself.
The server must confirm the matching reservation/metadata. Failed cleanup retains a
retry that can confirm the already-ready record safely. The history page exposes
pending local saves, including when remote list loading fails.

cancel_resident_media_request cancels by owner-scoped key, even when preparation
never committed or was rejected at quota. It creates a deleted tombstone if no row
exists, serializing with delayed prepare so a cancelled upload cannot appear later.
For an existing reservation it transitions to delete_pending. The client then uses
Storage API remove and finish_resident_media_delete. Finish refuses while an object
still exists. Interrupted removal stays visible/retryable; it does not report deletion
success early. No production SQL deletes storage.objects rows.

All media HTTP operations use a separate nonpersistent Supabase client pinned to the
captured access token, including Storage requests. Session identity is checked between
stages. An in-flight operation can still finish for its ORIGINAL owner; it cannot use
a later account's token. Collection disposal hides private state and invalidates stale
responses. Starting a mutation invalidates pre-mutation list responses. Auth permission
refresh hides routed detail content while keeping its component tree mounted, allowing
native photo picker selection to survive foreground checks. Access failure redirects
and unmounts it. The root Auth overlay remains in place.

## Image and product behavior

Images selected from camera/gallery or scanned locally are re-encoded as JPEG, resized
to at most 1280 pixels on their longest side and limited to 2 MiB. Selection cancellation
preserves an existing preview; selection removal before Save makes no network request.
A ready report photo can be removed without deleting its text/activity. Scan history
contains saved suggestions and photos, with separate incomplete/removal states and
bounded cursor pagination. Reanalysis of the same captured photo reuses its request
key; selecting another photo generates a new key. A removed key cannot be reused.

Storage MIME and SQL metadata checks do NOT inspect image bytes on the server. JPEG
normalization/header checks occur in the client, which is untrusted. Antivirus,
server-side image decoding/EXIF verification, content moderation, abuse rate limits,
automatic abandoned-upload cleanup and forensic audit logging are not implemented.
Neither image contents nor model results are promoted to trusted business evidence.

## Validation and deployment boundary

Local suites retain all identity, community and report submission assertions and add
52 media/Storage-policy assertions with a LOCAL provider metadata shim. The shim is
under backend/test only and MUST NEVER be executed on hosted Supabase. It is not a
real Storage service and cannot prove byte upload or provider metadata behavior.
Client regression tests include lost upload/finalization responses, durable-before-
remote ordering, bad payloads, account switching, cleanup failure, cancellation,
interrupted deletion, scoped reads and stale collection responses.

Deploy only the two appended migrations after preflight/dry-run review, configure the
private bucket, run read-only verification, and complete docs/media/ACCEPTANCE.md on
real signed-in sessions/devices. Do not mark hosted Storage or cross-platform acceptance
complete merely because local tests and bundles pass.
